# Next redesign mode (`/next`)

A second UI for cumora, served at `/next` on the same origin. `App.tsx` mounts `NextApp` in place of the classic Desktop/Mobile shells, so auth, stores, the WebSocket stream and mark-read logic are shared. Rules for changing it are in `AGENTS.md` next to this file.

## Switching

- A device that has not chosen opens `/` on a design choice, Modern or Classic, before sign-in (`auth/DesignChoice.tsx`), on the web and in the native apps alike; the public `app.*` host shows its WebShell instead. The pick is stored in `localStorage['cumora.ui']` (`next` or `classic`, `designPref.ts`), and `/` opens that design from then on. A device that never opened `/next` has no pick yet, so existing Classic web users see the choice once too.
- Opening a `/next` link stores `next` too.
- "Switch to classic design" in the workspace menu stores `classic`.

## Chat list

- Pinned rooms sit at the top as tiles that wrap onto new rows. Pin from a room's menu, or drag a room onto the tiles: while a room is dragged, a Pin slot (or a "Drop here to pin" zone when the last line is full) shows where. Drag a tile onto another to reorder the tiles, or back into the list to unpin it; on a phone, a tile's long-press menu has Move left and Move right. A pin is shared with the room's other members; the tile order is yours.
- Below them, rooms are grouped into your own categories, then Other. Other gets its header only once a category exists. A 1:1 room whose other member has left (a deleted agent or a removed member) is not listed. Create a category from the + menu, drag a room onto a category (or onto "Drop here for a new category"), and click a category header to collapse it. Drag a header to reorder the categories; every group folds while it moves. Right-click a header (long-press on a phone) for Rename, Move up, Move down, Mark all as read, Hide and Delete; Other's menu has Mark all as read. A hidden category leaves the list: the "N hidden" row at the bottom carries its unread count and opens it, and its menu has Show. On a phone, a room's long-press menu has "Move to".
- Categories, their order, hidden categories, collapsed groups and the tile order are personal and stored in the fork's SQLite database on the server, so they follow you across devices.

## Agents at work

An agent working in a room (it shows as typing there) sits on the composer bar instead of taking a row in the transcript. Its whole head pops up on the bar's top edge when it starts and shrinks away when it stops, and the messages never move, however many agents work. Past six heads on a phone and nine elsewhere, the rest share one "+N" head. Hovering a head shows the agent's name and how long it has worked; clicking the heads (tapping them on a phone) lists everyone at work, opens an agent's profile from its row, and stops one agent with its stop button when its engine can stop a turn. A reply that streams in shows in the transcript as it is written.

## Developer token figures

With developer mode on (workspace owners and admins), the transcript shows what the agents spent on model calls:

- Under the agents' last reply after each of your messages: the context of the agent's latest own call, with its model's window, and the cache hit ratio of every agent call from your message to your next one, or to now. A stretch without an agent reply shows nothing. A click (on a touch screen, Agent tokens in the reply's long-press sheet) opens the details per agent: the context, the cache hit ratio, the model calls, the whole prompt split into cache reads, cache writes and the uncached rest, the output, and each subagent the turns ran with its tokens, tool calls and time.
- A 1:1 room with an agent shows that agent's agenda turns (proactive work that answers no room) in one digest row after the message they followed: the agent, how many turns ran and when, the context from the first turn to the latest, and the cache hit ratio over all of them. A click opens a bar per turn (its context against the model's window, the share read from the cache filled in) and a table of each turn's context and cache hit. Turns whose cache hit fell under 90% get one line under the digest, however many there are. They count under no message.
- `GET /api/fork/rooms/:id/tokens` (`server/src/fork/tokens.ts`) reads upstream's `llm_calls` rows that the computer's daemon writes since it matches the engines' own records (`extras.acct = 2`): one row per model call and a `rest` row at each turn's end. Claude Code repeats a response's usage on each of its content blocks and reports the final output only when the response ends, so the daemon ledgers a response once and closes the turn with `result.modelUsage`, which also covers subagents. Codex reports the thread's running totals, and the first update a process sees counts a resumed thread's whole life. Rows from older daemons do not show. The room reloads the figures every 10 seconds while it is open.

## Message times

Each turn (one sender's unbroken run of messages) opens with the avatar and a name row carrying its time; your own messages carry theirs left of the bubble. Later messages in a turn show a time in the avatar column (right of the bubble in a 1:1 room, which has none) only after a gap, and a long silence inside a day gets a line saying how long it lasted (the thresholds are `STAMP_GAP_MIN` and `PAUSE_MS` in `chat/model.ts`). Every message keeps its time in place: hovering a message shows it, and clicking or tapping any time shows them all until the next click or until the room closes. The long-press sheet and the ⋯ menu start with the full date and the time to the second with the UTC offset.

Times carry no date. A chip marks where each day starts, and while the rows under the room header belong to a day whose chip is scrolled away, a pill under the header shows that day's date, so a room opened partway into an older day still says which day its times belong to. The pill takes the chip's place as the chip passes under the header and steps aside when the next day's chip comes up to it.

## Replying

On a touch screen, swipe a message left to reply to it: the message follows the finger, a reply arrow grows in beside it, and letting go once the arrow fills puts the message in the composer's reply chip. A swipe that starts on a code block wider than its bubble does not reply, and on a phone a swipe right still goes back to the chat list. With a mouse, Reply is on the message's hover toolbar and in its ⋯ menu; the long-press sheet has it too.

## Questions and secrets

An agent can put a card under its message (`server/src/fork/cards.ts`). Every computer agent's standing prompt says when to use one.

- **A question** (`cumora ask <room> "<question>" "<option>" "<option>"`, up to 8 options, `--body` for text above the question) puts a card marked "Needs an answer" under the message, with the options as chips and a field for an answer in the person's own words. The first person to answer closes the card for everyone. The card then shrinks to a summary: the answer, who gave it and when, and the other options behind a toggle. The answer is posted as that person's reply quoting the question, so it wakes the agent like any reply. The transcript draws that reply as one line at the time it was sent ("✓ Maya answered “…”"), which opens the question; the thread leaves it out. A message that quotes the question or that reply names the question above its bubble ("Re: …") instead of quoting it, and every computer agent's standing prompt tells it to quote the reply when it acts on it. While an agent's newest question in the room is open and scrolled out of view, a pill above the composer says that the agent is waiting and goes to it. A question the agent asked past keeps its card but gets no pill: the agent asked again, or a person wrote after the question (an answer in their own words, or something else) and the agent spoke after that. Whatever the agent said counts, so in a room with several agents a question can lose its pill while its agent talks about something else. An answer whose reply never got posted, because the server restarted in between, opens the card again within a minute of the restart.
- **A secret** (`cumora secret request <room> "<what it is for>"`) shows a masked field that keeps the lines of a pasted key or certificate (Enter sends and Shift+Enter breaks a line; on a phone, Return breaks a line and the button sends). The secret is never part of a message. The person's reply only says that it was sent, and the server keeps the value sealed (AES-256-GCM, with a key derived from `AGENT_RUNTIME_SECRET`) until the agent runs `cumora secret take <message_id> <path>`. That command works once, for the agent that asked while it is still in the room, and only through the computer's `cumora` shim: the shim creates `<path>` before it asks (a new file, mode 600, never a `.md` file, which the Handbook records), writes the secret into it instead of printing it, and the server forgets it. A take that has started finishes even if its command is stopped. A secret nobody takes is deleted within a minute after its day is over. The card then reads "saved" or "deleted".
- The classic UI shows these messages as plain text. A question can be answered there with a typed reply, but a secret can be sent only from this UI.

## First question

A new agent does not wait to be spoken to. Right after it is hired (`POST /api/agents`), the server wakes it in its 1:1 room with the person who hired it, with the same system message a trigger fires (`calendar_event`, `eventKind: 'hired'`, posted through `server/src/fork/dispatch.ts`), which the transcript does not show (`server/src/fork/firstQuestion.ts`). The brief names that person and has the agent greet them in their language and ask with a question card what they want it to do, with three or four options that fit its name, role and style, which its `CLAUDE.md` or `AGENTS.md` carries. The wake also brings the shared memory below, so an agent hired later already knows what earlier ones learned about that person. It is posted once, as a best-effort step of the hire: a retried hire that finds the agent it already made posts nothing, and a failed post is only logged, which leaves the agent waiting to be spoken to. The agent asks once its computer picks it up, within a minute.

## Shared memory

Every agent on a computer shares one memory folder, `~/.cumora/shared-memory/`, beside its own `memory/`: who the people they work for are, what to call them, the language and time zone they use, and which accounts they all use, but no secrets and nothing that belongs to one room or project (`server/src/fork/sharedMemory.ts`). The daemon adds the folder's `MEMORY.md` to every wake after the agent's own index, and the standing prompt says what belongs there. Agents write the files themselves, which only an unsandboxed engine can do (cumora-setup's computer runs them so); a sandboxed agent still gets the index, and its standing prompt says the folder is closed to it. Every agent reads the index on every wake, so text that any agent with write access was tricked into saving there reaches all of them; give agents that access only where you accept that. The Handbook does not show this folder.

## Agents

The Agents section opens on a wall (`sections/agents/Wall.tsx`): one tile per agent with its state and role. For workspace owners and admins, the tile of an agent on a computer also shows a small copy of its browser (`ScreenThumb` in `panel/ComputerTab.tsx`, one frame every 3 seconds, read only while the tile is on screen and the app is in the foreground) and the T3 Code thread it is on, or its newest one. Neither is read while an agent's page is pushed over the wall on a phone. `?roster=list` shows the list beside the open agent instead, with the human teammates; both use the same filters (`?filter=`). A click on a tile or a row opens the agent's page, which on the wall fills the section with a back bar. For owners and admins, the first view of a computer agent's page is its workspace (`sections/agents/Work.tsx`): its browser large, beside its T3 Code threads and the Handbook's three newest changes of the week. `?view=profile` and `?view=handbook` show its profile and its Handbook.

The agent menu (`agentMenu.tsx`) opens from every place that names an agent. A click, a right-click (a long press on Android), Enter or Space, or the context-menu key opens it on an avatar or a name in the transcript, an agent's row in the Members tab, and the name in the header of a 1:1 room with an agent (which opens this menu instead of Edit there); an @mention opens it on a click or a right-click, since the classic chip takes no focus. On a wall tile or a list row, whose click opens the agent, a right-click or a long press opens it. Any element marked `data-agent-id` gets these triggers from one listener on the app's root element; it runs before React's own handlers, so the classic @mention chip (`components/Message.tsx`) opens this menu instead of its profile pane. The menu shows what the agent is on now and, for owners and admins and an agent on a computer of its own (never a Cumora Cloud agent), Live screen (key S) and Coding (J) with its three newest threads (one with a pull request opens it). Then come Message (M), Mention here (@, in a room the agent is in: it adds `@<id>` to the composer), Stop this turn (no key, so a stray key never ends a turn; only while the agent is typing in this room on an engine that can stop, since the daemon stops whatever turn is running), View profile (I) and Copy link (C). The menu stays current while it is open. A row whose request fails (Message, Stop this turn, Copy link) opens the menu again where it was, with what went wrong under its header. Inside a chat, Live screen, Coding and View profile open the agent drawer in the room panel (`panel/AgentDrawer.tsx`, `?peek=agent:<id>&pane=screen|jobs|profile`; without `pane` it shows the profile), with the same screen, thread list and profile as the workspace, so the conversation stays in view; anywhere else they open the agent's page. A person in the Members tab opens the drawer on their profile.

A right-click while any menu is open never brings up the browser's own menu: on the menu it does nothing, and outside it the open menu closes and the right-click reaches what is under it, so another row's menu opens at once (`rightClickThrough` in `ui/primitives.tsx`).

## Handbook

The room panel's first tab, and the Handbook view of an agent's profile, show one agent's standing files as one document: its `CLAUDE.md` or `AGENTS.md`, its memory (`memory/**/*.md`, `MEMORY.md` first), its own skills (`.claude/skills/*/SKILL.md`) and the skills every agent on the computer shares. A skill the selected range did not change shows only its name; opening it shows the whole file. In a room with several agents, the chips at the top pick one (`?agent=`).

The tab opens on the changes, not on the document, whose instructions alone outrun a phone screen:

- **The map** draws the whole document as short bars, one column per section and one bar per line (a long section merges neighbouring lines, keeping a change's colour), with each changed line in its colour: green added, red removed, the primary colour rewritten.
- **Excerpts** list the range's newest 20 changes, newest first: the file, the line where the change starts, its first six lines and the note. Older ones are marked only in the full text.
- **Full text** is folded. Pressing a spot on the map, an excerpt's head or "Show all N lines" opens it at that place under the toolbar.

- **Changes since** Today (midnight in your time zone), 7 days, 30 days or All time (`?since=`): removed words are struck through in red, added ones tinted green, and each change has a number. The note under a change names the person whose message most likely caused it and quotes the message, which opens in its room. A message from a room you are not in shows who wrote it and when, nothing more.
- **The scrubber** has a stop for every change and shows the document as it was right after it (`?at=`). Its far end is now, which keeps up with new changes.
- **Who can see it:** workspace owners and admins only, because an agent's files can quote any room. Text is redacted for tokens, keys and passwords.

The computer keeps no history of these files, so the server records one. `server/src/fork/recorder.ts` polls the files compose mounts read-only under `server/computer/` and stores every version in the fork's SQLite. The first version of a file in a home seen for the first time is a baseline, not a change, and a deletion is stored as a version too. A change belongs to the agent's run that was open at the file's mtime. Its instruction is the newest message a person wrote before that run started, in a room the agent posted in during the run (in its 1:1 rooms when it posted nowhere) and after its previous run started. The tab reads `GET /api/fork/agents/:agentId/handbook?since=&at=` (`server/src/fork/handbook.ts`) and polls it while it is open (`panel/handbook.ts`). While the scrubber or the range changes, the previous document stays on screen, dimmed, until the new one arrives, so dragging the scrubber never blanks the tab.

## Deleting an agent

Off-boarding keeps everything so the agent can be re-hired. An off-boarded agent's profile then offers "Delete permanently" (`?purge=1`), for owners and admins: `DELETE /api/fork/agents/:agentId` (`server/src/fork/purge.ts`) removes the agent, its 1:1 rooms, its memory, log, workspace, tasks, runs and routines, its look, triggers and Handbook versions. What it wrote in rooms that stay (messages, comments, documents, reactions, votes) and the usage ledgers stay under a new `deleted:<hex>` author, which the app shows as "Deleted agent". The id itself is never given out again (the fork's `purged_agents` table, read by `server/src/agents/create.ts`): ids are slugs of the name, so an agent hired later under the same name gets another one, and nothing that still names the old id reaches it. The agent's computer removes its home, its engine sessions and the Claude Code transcripts that ran in its home at its next agent sync (`server/src/fork/computer-purge.ts`, queued in the fork's `computer_purges` table); Codex threads stay in the computer's shared Codex database.

## Edit

The room panel's tabs are Handbook, Coding, Computer, Members (not in a 1:1 room), Files and Routines. The room's settings are not a tab: **Edit** opens them in a dialog over the chat (`panel/EditDialog.tsx`, `?edit=1`), from the room's name in the chat header (in a 1:1 room with an agent the name opens the agent menu) or the pencil in the room panel's header. **This room** holds the room's own settings: the name (group rooms), the topic, pin and mute. Below it, workspace owners and admins get the room's agent: its name, role, bio and style save when the field loses focus, and "Model, computer and avatar" opens the full agent editor over it (`?agent-edit=<id>`, the same editor as the Agents section). An agent's settings follow it into every room it is in, which the card says. In a room with several agents, the chips pick one (`?agent=`, shared with the Handbook). Start a live session and, in a group room, Leave room come last.

## Coding tab

The room panel's Coding tab (`panel/CodingTab.tsx`) lists the T3 Code threads the room's agents launched, for workspace owners and admins only: newest change first, ten per agent, with the agent's face and name when the room has several. A row shows the thread's status (running, needs an answer, finished, failed, stopped, idle), when it started or stopped, and its pull requests; a row with pull requests opens the last one T3 lists. A failing T3 server or a failed reload is named under the threads. The tab reads `GET /api/fork/agents/:agentId/coding` when it opens, when the server sends `fork.coding` to the workspace (its copy changed, or a T3 server started or stopped failing), when the socket reconnects and when the app comes back to the foreground, and keeps the last answer per agent, so it draws at once when the tab opens again. T3 does not record which MCP client made a thread, so the computer puts `[@<agent id>] ` before the title of each `t3_thread_launch` an agent makes, or `[@<name> · <agent id>] ` once the agent's current name no longer matches its id, which keeps the name the agent was created with (a hook in both Claude Code and Codex, `computer/t3-tag.mjs` in the deploy repo), and `server/src/fork/coding.ts` reads every project of each T3 server for that mark and copies the threads into the fork's SQLite. Every 3 seconds it asks whether T3 may be changing a marked thread on a server (an agent's busy status was set or renewed within its 90-second lease, or a copied thread on that server is still moving) and reads the server then; otherwise it reads it once a minute. Each server has its own loop, so one that sleeps holds back nothing. When a thread finishes, fails or is stopped, or asks a question (a pending request in T3), the server wakes its agent once per run and status, and once per question, with a `calendar_event` message as a trigger does. The message names only the server and the thread, since the room can read it. It goes to the room of the turn that launched the thread: the room on the first turn call the agent records from the launch on, which the computer's daemon puts on each call (Claude Code records each model call as it ends, Codex a whole turn when it ends, so a wake waits until then). A launch from a turn that answered several rooms at once wakes nobody. Without compose's T3 server list (`server/computer/t3code.json`) and tokens (`server/computer/t3code/`), the tab stays empty. The agent drawer, the Agents wall and workspace and the agent menu read the same lists (`useCoding`).

## Computer tab

The room panel's Computer tab (`panel/ComputerTab.tsx`) shows the browser of one of the room's agents live, with chips to pick another agent in a room with several, for workspace owners and admins only, because the browser shows every site the agent is signed in to. A link to it is `/next/c/<room id>?panel=computer` (plus `&agent=<id>`). The computer runs one headless Chromium per agent with agent-browser, in the session named after the agent (the shims in the deploy repo), and agent-browser's dashboard streams each session's screen and takes input for it. `server/src/fork/screen.ts` finds the agent's session in the dashboard's list, holds one stream per agent while anyone polls, and answers `GET /api/fork/agents/:agentId/screen?after=<seq>` with the browser's state, its address and the newest frame when one arrived after `after`, waiting up to 5 seconds for a change. Long polls rather than a stream, because the phone app's fetch goes through native HTTP (CapacitorHttp), which hands over a response only when it ends. The dashboard listens on the computer's loopback; the deploy repo relays it to `computer:4849` on the compose network, and the server asks as `localhost:4848`, which the dashboard admits without its access token. A browser that is not open is looked for every 3 seconds, and a stream nobody polled for 30 seconds closes. The tab draws frames into a canvas and polls only while the app is in the foreground. A click, a drag and a wheel turn on the screen, and keys while it has focus, go to `POST /api/fork/agents/:agentId/screen/input` in order, one request at a time; on a touch screen a tap clicks and a vertical drag scrolls. Text that a phone keyboard, an IME or the clipboard produces goes through the field under the screen, character by character, beside Tab, Backspace and Enter buttons. The expand button opens the same screen large in a dialog, and the panel's copy stops polling meanwhile. The agent drawer and the Agents workspace show the same screen (`Screen`); the Agents wall shows `ScreenThumb`, which reads one frame every 3 seconds per tile on screen, after its first read with `wait=0` so the server answers at once instead of holding the connection, and so keeps each of those agents' streams open on the server.

## Routines tab

The room panel's Routines tab lists the Calendar agent tasks that post into the room, one row per job with one switch. A task booked without a room (an agent's `cumora calendar create` without `--in`) posts into a 1:1 room holding its creator and its assignee, and is listed there (`postsInto` in `panel/routines.ts`). Calendar repeats at most daily, so an agent that wants a job every few hours books one daily event per time; events with the same agent, prompt and repeat rule whose titles share a stem fold into one job (`panel/routines.ts`), shown as "Every 3 hours · next 06:07". A job opens in place (`?routine=<event id>`) with its prompt, Run now, a switch per time, and **Repeats**, which turns a daily job into every 1, 2, 3, 4, 6, 8, 12 or 24 hours from its earliest time: times already booked stay with their run history, missing ones are created (starting at their next occurrence, so none fires on creation) and the rest are deleted. A time, like an event link in a message, opens the event in the panel (`?peek=event:<id>`) with the Calendar section's own detail; its Edit goes to Calendar.

Under the jobs come the room's **triggers**: routines that fire when a pull request merges in a GitHub repository instead of at a time (`panel/triggers.tsx`, `server/src/fork/triggers.ts`). A trigger names the repository, the gh profile on the computer that reads it (compose mounts the computer's `~/.config/gh` read-only under `server/computer/gh`), the agent and the prompt. The server polls each repository once a minute with a conditional request and posts, for every pull request merged after the trigger was made, the same system message as a Calendar firing (`calendar_event` with `eventKind: 'trigger'`, through upstream's own `postDispatchMessage`), so the agent wakes as it does for a routine and the transcript shows nothing. A merge fires once (`trigger_fires` in the fork's SQLite). A trigger opens in place (`?trigger=<id>`) with Run now, which fires the repository's latest merge again, its last fire and any polling error, and Delete. **New trigger** at the bottom of the tab creates one for the room. Agents list, create and delete triggers with `cumora trigger` (`runTriggerCli` in `server/src/fork/triggers.ts`), under the same rule: only in rooms they are in, and only for agents in that room. An agent cannot add a second trigger for the same repository and agent to a room, nor delete a trigger a person paused: a pause is theirs to lift. Since an agent may have written a trigger's title and prompt, the tab and `cumora trigger list` show both through `server/src/fork/redact.ts`; a fire still posts the prompt as written.

A Calendar firing is a system row that wakes the agent. The transcript does not show it, and it is not unread, not the chat-list preview and not a reason to move the room up the list (the list query in `server/src/api/router.ts` leaves it out, and the live patch in `stores/conversations.ts` matches). A jump to one, from an event's run history, lands on the next thing in the room.

## Haptics

In the phone app, switching sections answers with a click when the finger lands. Opening a room from the chat list and toggling a reaction answer when the tap ends instead: they sit in lists that scroll, where a finger that lands may be starting a scroll, so a scroll plays nothing. A long press answers with a deeper click, a message swiped far enough to reply with a tick, sending a message with one click, and someone else's message arriving in the open room with a double click (not in muted rooms, at most once every 2 seconds). A save the user waited on ends with a success or error haptic. Android plays the system's own effects, so the phone's touch-feedback setting turns them off. The web and the desktop app have none.

## Animated avatars

An agent can wear a live [bloub](https://github.com/jeremy-prt/bloub) instead of its portrait. Owners and admins choose it in the agent editor (Edit on the profile, or "Model, computer and avatar" in a room's Edit), whose Avatar section switches between Portrait and Animated. It previews the draft where people meet it, at those sizes: a message, a member chip, a mention, and beside up to four other agents. The first Animated look is random, in a color no other agent wears while one is left; colors other agents wear are dimmed, and a color or look another agent already has is named. "Play a moment" plays idle, thinking, working, a posted message, and a happy or a sad reply on the preview. The editor's Save keeps the avatar with the rest of the profile; Paint with AI saves a new portrait at once.

People pick the shape, the color and any number of accessories: cat ears and whiskers (`bloub/accessories.ts`). The ears sit on the body outline the engine draws each frame, so they breathe, squash, lean and spin with it, go in when the body shrinks to a dot and come back with the ball, follow the face (up when surprised, flat when angry, drooping when sad, one down when confused) and now and then flick. Whiskers follow the eyes. A bloub with ears draws in a taller box, so the ears stay inside the avatar. The face follows the agent's messages: for every message an agent that wears a bloub posts, `server/src/fork/mood.ts` asks TypeSafe Jev (OpenRouter's decisions API, `OPENROUTER_API_KEY`) which of 16 faces fits it, stores the face with the look, and sends `fork.agent.mood` to the workspace. The face stays until the agent's next message; without the key, faces stay at rest. The look belongs to the agent for the whole workspace and is stored in the fork's SQLite database (`GET/PUT/DELETE /api/fork/bloub-avatars/:participantId`; a PUT without `accessories` keeps the ones the agent wears, so an app built before them cannot take them off), so the classic UI, push notifications and email keep showing the portrait. The redesign loads the looks on start and whenever the app comes back to the foreground.

Every avatar of the agent plays what it is doing (`bloub/program.ts`):

| Agent | bloub |
| --- | --- |
| Available | `idle`: gaze drift and blinking |
| Thinking | `thinking`: three pulsing dots |
| Working with a tool it can name | Leans back and acts it out with a prop it looks at: a page read line by line (Read, `cumora glance`), a pen writing on the page (Write, Edit, `cumora reply`), a terminal (Bash), a magnifier (Grep, Glob), a globe (WebFetch, WebSearch) |
| Working with another tool | `play` and `orbit` in turn |
| Waiting | `notify`: the blue dot |
| Offline (its computer is off, resting or off-boarded) | `sleep`: a small bouncing dot |
| Starts a turn | `burst` before the busy state |
| Ends a turn | `comet` before `idle` |
| Posts a message | `wink`, then back to its state, wearing the face Jev picks for the message |

A status that flips back within a moment does not flash a state: the first change shows at once, and each state then stays at least 1.2 s, the latest status winning. BYOA agents report `working` from the first engine hop that calls tools to the end of the turn and keep their status alive through the whole turn (`server/src/agents/computer/daemon.ts`); with it they send the kind of tool (`server/src/fork/toolKind.ts`), which the server passes to the clients as `fork.agent.tool` straight over Redis, so a client that missed it shows the generic work until the next one. Codex reports one hop per turn, so its agents stay on `thinking`. With reduced motion, each state is drawn once and settled, without the turn effects.

## Local verification

The redesign can run against a throwaway local backend:

1. Postgres + Redis in the `default` Colima profile (never the `circlechat` one), migrate with `npx tsx server/src/migrate-bin.ts`, start `npx tsx server/src/index.ts` with `DATABASE_URL`, `REDIS_URL`, a dummy `OPENAI_API_KEY` and `CUMORA_PUBLIC_ORIGIN` set to the origin the device opens (the Vite server, which proxies `/uploads`). Upload URLs carry that origin, so the default `http://localhost:5181` breaks uploaded images and portraits on any other device. The server seeds demo agents and rooms on first boot. `server/data/fork.sqlite` is created on the first `/api/fork` request, which opening the redesign's chat list sends, or at boot when `server/computer/` exists (step 4).
2. Mint a session with `createSession` from `server/src/auth.ts` and open `/next#token=<token>&companyId=personal`.
3. Live states (typing, streaming, working) can be driven from the browser console in dev: `(await import('/src/stores/messages.ts')).useMessages.setState(...)`.
4. For the Handbook, put sample files under `server/computer/agents/<agent id>/` and `server/computer/skills/<name>/SKILL.md` (gitignored) before starting the server; editing one afterwards records a change. A row in `agent_runs` around the file's mtime and a person's message before it show the attribution.
5. To try the Android app against it: `adb reverse tcp:<port> tcp:<port>`, set `"server": {"url": "http://localhost:<port>"}` in the generated `android/app/src/main/assets/capacitor.config.json` (the debug build allows cleartext only to localhost), build with `./gradlew assembleDebug`, and rebuild the production APK afterwards.
